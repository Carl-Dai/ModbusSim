# auto-update 规范

## 目的

应用内自动更新：在启动时与手动触发时检查 GitHub Releases 上的新版本，校验版本清单与 minisign 签名，在用户确认后下载安装并重启，不做静默强制更新；检查按固定顺序轮询多个 endpoint 以适配国内网络，并支持 24 小时「稍后提醒」。

## 需求

### 需求:启动时静默检查更新
应用启动后必须延迟约 2 秒自动检查一次更新；该检查失败时禁止打扰用户（仅记录日志）。距上次检查不足 6 小时时，自动检查必须直接跳过（节流）。

#### 场景:启动发现新版本
- **当** 应用启动且距上次检查超过 6 小时，远端 manifest 版本高于当前版本
- **那么** 弹出更新对话框，展示新版本号、更新说明与发布日期

#### 场景:节流期内启动
- **当** 应用启动且距上次检查不足 6 小时
- **那么** 不发起网络请求，不弹窗

#### 场景:检查失败静默
- **当** 启动自动检查时所有 endpoint 均不可达
- **那么** 仅在控制台记录警告，界面无任何提示

### 需求:手动强制检查更新
用户必须能从界面主动触发更新检查；手动检查必须无视 6 小时节流与 24 小时 snooze。手动检查失败时必须向用户展示错误，已是最新版本时必须明确告知。

#### 场景:手动检查发现新版本
- **当** 用户点击"检查更新"且远端存在更高版本（即使该版本处于 snooze 期）
- **那么** 弹出更新对话框

#### 场景:手动检查已是最新
- **当** 用户点击"检查更新"且当前已是最新版本
- **那么** 界面明确提示"已是最新版本"

#### 场景:手动检查网络失败
- **当** 用户点击"检查更新"且所有 endpoint 均不可达
- **那么** 界面展示检查失败的错误信息

### 需求:稍后提醒 (snooze)
更新对话框必须提供"稍后提醒"操作；选择后系统必须在 24 小时内不再就同一版本自动弹窗。出现更高的新版本时 snooze 必须失效。

#### 场景:snooze 同版本
- **当** 用户对版本 X 选择"稍后提醒"，24 小时内自动检查再次发现版本 X
- **那么** 不弹窗

#### 场景:snooze 期间出现更新版本
- **当** 用户对版本 X 选择"稍后提醒"，自动检查发现版本 Y（Y > X）
- **那么** 正常弹出版本 Y 的更新对话框

### 需求:下载安装与重启
用户确认更新后，系统必须下载更新包、校验签名、安装并重启应用；下载过程中必须展示进度百分比。

#### 场景:正常更新流程
- **当** 用户在更新对话框点击"立即更新"
- **那么** 显示下载进度（0–100%），下载完成后自动安装并重启到新版本

#### 场景:签名校验失败
- **当** 下载的更新包 minisign 签名与内置 pubkey 不匹配
- **那么** 中止安装并向用户展示错误

### 需求:多 endpoint 容灾
更新检查必须按固定顺序轮询多个 manifest endpoint（自建代理 → GitHub 直连 → 公共代理），任一成功即停止。manifest 中的下载 URL 必须与所属 endpoint 使用相同的代理前缀。

#### 场景:首选 endpoint 不可达
- **当** 首个 endpoint 超时或返回错误
- **那么** 自动尝试下一个 endpoint，直至成功或全部失败

#### 场景:代理 manifest 的下载地址
- **当** 更新检查命中某代理 endpoint 的 manifest 变体
- **那么** 后续更新包下载 URL 同样经由该代理前缀

### 需求:发布产物签名与 manifest 生成
release 流程必须为每个更新产物生成 `.sig` minisign 签名，并在所有构建 job 成功后生成并上传 slave/master 各 5 份 manifest 变体（每代理一份 + 直连一份）。任一产物缺失 `.sig` 时 manifest 生成必须失败中止。

#### 场景:正常发版
- **当** 推送版本 tag 且全部构建 job 成功
- **那么** Release 资产包含各平台更新包、对应 `.sig`，以及 `latest-slave*.json` / `latest-master*.json` 共 10 份 manifest

#### 场景:签名缺失
- **当** 某构建产物无对应 `.sig` 文件（如 secrets 未配置）
- **那么** publish-manifest job 报错退出，不上传任何 manifest
